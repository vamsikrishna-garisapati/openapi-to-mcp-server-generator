# RFC-002: OpenAPI Parser Specification (Revised)

**Project:** MCP Studio

**Version:** 2.0 (Architecture Freeze)

**Status:** Approved

---

# 1. Purpose

This RFC defines the **behavioral specification** of the Parser: supported inputs, transformation rules, and output contract.

Implementation details (file layout, component names, warning/error codes) are specified in **RFC-005**.

The Parser is the only module allowed to understand OpenAPI. It produces an immutable `ApiModel` defined in **IR.md**.

---

# 2. Public Interface

```ts
interface Parser {
    parse(document: RawDocument): Promise<Result<ApiModel>>;
}
```

The Parser does not load files (Loader), generate MCP code (Generators), or package ZIP archives (Packager).

---

# 3. Supported Input

Supported:

* OpenAPI 3.0.x
* OpenAPI 3.1.x
* JSON and YAML formats

Not supported:

* Swagger 2.0
* RAML, API Blueprint, GraphQL, SOAP, AsyncAPI

Input arrives as a `RawDocument` from the Loader.

---

# 4. Internal Pipeline

The Parser owns the full OpenAPI → IR pipeline. Stages run in this fixed order:

```text
RawDocument
      │
      ▼
Parse JSON/YAML
      │
      ▼
Validate
      │
      ▼
Resolve References
      │
      ▼
Extract Metadata
      │
      ▼
Extract Servers
      │
      ▼
Extract Authentication
      │
      ▼
Extract Endpoints
      │
      ▼
Extract Schemas
      │
      ▼
Assign Tool Names
      │
      ▼
Select Primary Responses
      │
      ▼
Build ApiModel
```

See RFC-005 for component-level implementation.

---

# 5. Validation

The validator checks:

* OpenAPI version (3.0.x or 3.1.x only)
* Required sections (`paths`, etc.)
* Operations, parameters, and schemas
* **Duplicate `operationId` values across operations (fatal error E006)**

Fatal errors stop parsing. Warnings do not.

---

# 6. Reference Resolution

* Resolve all internal `$ref` references
* Detect circular references without infinite recursion
* Represent circular schema graphs safely in the IR

No unresolved references may reach the IR Builder.

---

# 7. Metadata Extraction

Populate `ApiInfo`:

* `title`
* `version`
* `description` (optional)

---

# 8. Server Extraction

Version 1 supports one server.

* Use `servers[0].url` when present
* If `servers` is missing or empty: set `baseUrl` to `""`, emit warning **P004**, require runtime `BASE_URL`

---

# 9. Authentication Extraction

Supported schemes:

* API Key (`type: apiKey`)
* HTTP Bearer (`type: http`, scheme: bearer)

Populate `Authentication` per IR.md:

* `id`, `type`, `location`, `parameterName`, `envVariable`

Bearer normalization:

* `location = "header"`
* `parameterName = "Authorization"`
* `envVariable = "ACCESS_TOKEN"`

Unsupported schemes produce warning **P003** and are omitted from the IR.

---

# 10. Security Assignment

For each endpoint, populate `Endpoint.authentication` with `Authentication.id` values:

1. Global OpenAPI `security` applies to all operations by default
2. Operation-level `security` replaces global security for that operation
3. `security: []` on an operation means no authentication (`authentication: []`)
4. No security defined anywhere → `authentication: []`

---

# 11. Endpoint Extraction

Each OpenAPI operation becomes one `Endpoint`.

Extract before naming:

* method, path, summary, description, tags
* `deprecated` flag
* parameters, request body, responses

Naming occurs in a separate stage (Section 12).

---

# 12. Endpoint Naming

The Parser assigns both `Endpoint.id` and `Endpoint.name` (same value in v1).

Rules:

1. Use `operationId` if present
2. Otherwise derive from HTTP method + path
3. Convert to snake_case
4. Deduplicate derived-name collisions with numeric suffixes (`_2`, `_3`)

**Duplicate `operationId`** is caught during validation (Section 5) and is fatal before naming runs.

---

# 13. Request Body Extraction

Supported: `application/json` only.

Other content types (multipart, XML, plain text, octet-stream) produce warnings and are omitted from the IR.

---

# 14. Response Extraction

Extract all responses (status code, description, schema).

Set `Endpoint.primaryResponse` using this priority:

1. `200`
2. `201`
3. `default`
4. First available response

Generators use `primaryResponse` only; they never re-run this logic.

---

# 15. Schema Normalization

Map OpenAPI types to IR `Schema` per IR.md:

| OpenAPI | IR      |
| ------- | ------- |
| string  | string  |
| integer | integer |
| number  | number  |
| boolean | boolean |
| object  | object  |
| array   | array   |

Also preserve: `enum`, `default`, `examples`, `nullable`, `format`, object `required[]`, array `items`.

---

# 16. Unsupported Schema Features

Not represented in the IR:

* `oneOf`, `anyOf`, `allOf`
* discriminator
* xml metadata
* binary formats

Behavior: emit warning **P002**, continue parsing if the endpoint remains usable without the unsupported construct.

---

# 17. Deprecated Endpoints

Deprecated operations are included with `deprecated: true`.

Emit warning **P005**. Generators append `(Deprecated)` to tool descriptions (RFC-001).

---

# 18. Warning and Error Models

Warnings include `code`, `message`, and `location`. They never stop parsing.

Standard warning codes (see RFC-005 §16):

* P001 Missing Description
* P002 Unsupported Schema
* P003 Unsupported Authentication
* P004 Missing Server
* P005 Deprecated Endpoint

Fatal errors stop parsing immediately.

Standard error codes (see RFC-005 §17):

* E001 Invalid OpenAPI
* E002 Missing Paths
* E003 Invalid Schema
* E004 Unresolved Reference
* E005 Unsupported OpenAPI Version
* E006 Duplicate operationId

---

# 19. Parser Output

```text
Result<ApiModel>
├── data: ApiModel
├── warnings: Warning[]
├── errors: GenerationError[]
└── statistics
```

Statistics (runtime metadata, not stored in IR):

* endpoint count, schema count, parameter count
* warning count, references resolved
* parse duration

# 20. Performance Goals

| Spec size        | Target   |
| ---------------- | -------- |
| Small (<50 ops)  | < 2 sec  |
| Medium (50–300)  | < 5 sec  |
| Large (>300)     | < 20 sec |

# 21. Test Requirements

* Unit tests for each internal parser component (RFC-005 §19)
* Integration tests: Petstore, small custom API, broken documents
* Verify produced `ApiModel` matches IR.md invariants

End-to-end generation golden tests are specified in RFC-006.

# 23. Definition of Done

RFC-002 is complete when:

* Parser behavior matches this RFC and IR.md
* Implementation follows RFC-005
* No OpenAPI objects leave the Parser public interface
* Warning and error codes are standardized
* Parser unit and integration tests pass
