# RFC-003: MCP Generator Specification (Revised)

**Project:** MCP Studio

**Version:** 2.0 (Architecture Freeze)

**Status:** Approved

---

# 1. Purpose

The MCP Generator converts an `ApiModel` into a complete, compilable TypeScript MCP server.

The generator has no knowledge of OpenAPI.

It consumes only the Internal Representation (IR).

---

# 2. Responsibilities

The Generator is responsible for:

* Building ViewModels
* Rendering templates
* Generating project files
* Generating configuration
* Producing a compilable project

The Generator is **not** responsible for:

* Parsing OpenAPI
* Validation
* Endpoint naming
* Authentication normalization
* Schema normalization
* Primary response selection

Those responsibilities belong to the Parser.

---

# 3. Input / Output

Input

```text
ApiModel
```

Output

```text
GeneratedProject
```

A GeneratedProject is an in-memory collection of files and directories ready to be written to disk.

---

# 4. Generator Architecture

```text
ApiModel
     │
     ▼
ViewModel Builder
     │
     ▼
Generators
     │
     ▼
Generated Files
     │
     ▼
Project Builder
```

The Generator never writes files directly.

---

# 5. Generated Project Layout

```text
generated-server/

├── package.json
├── tsconfig.json
├── Dockerfile
├── README.md
├── .env.example
│
└── src/
    ├── index.ts
    ├── client.ts
    ├── config.ts
    │
    ├── auth/
    │   └── auth.ts
    │
    ├── tools/
    │   ├── create_user.ts
    │   ├── update_user.ts
    │   └── delete_user.ts
    │
    └── utils/
```

This structure is fixed for Version 1.

---

# 6. Generator Modules

The generator consists of the following modules:

* MCP Server Generator
* Tool Generator
* HTTP Client Generator
* Authentication Generator
* Configuration Generator
* Package Generator
* TypeScript Config Generator
* Docker Generator
* README Generator
* Environment Generator

Each module owns exactly one output (or copies one static template).

---

# 7. ViewModel Builder

The ViewModel Builder transforms IR objects into template-ready objects.

Example

```text
Endpoint
        │
        ▼
ToolViewModel
        │
        ▼
tool.hbs
```

Templates never receive `ApiModel` directly.

---

# 8. MCP Server Generator

Generates:

```text
src/index.ts
```

Responsibilities:

* Create MCP server using `@modelcontextprotocol/sdk`
* Register generated tools
* Configure stdio transport
* Start the server

Version 1 uses **stdio transport only** via `StdioServerTransport` from the official MCP SDK.

---

# 9. Tool Generator

Each Endpoint generates exactly one tool file.

Input

```text
Endpoint
```

Output

```text
src/tools/{endpoint.id}.ts
```

Example

```text
Endpoint.id

↓

create_user

↓

src/tools/create_user.ts
```

---

# 10. Tool Registration

All generated tools are automatically imported and registered in `src/index.ts`.

No manual registration is required.

---

# 11. Authentication Generator

Generates

```text
src/auth/auth.ts
```

Responsibilities

* Load credentials from environment variables
* Build authentication headers/query/cookies
* Validate required credentials
* Expose helper methods for the HTTP client

Authentication behavior comes entirely from the IR.

---

# 12. HTTP Client Generator

Generates

```text
src/client.ts
```

Responsibilities

* Create shared Axios instance
* Configure Base URL
* Inject authentication
* Configure timeout
* Handle JSON serialization

Retries are not implemented in Version 1.

---

# 13. Configuration Generator

Generates

```text
src/config.ts
```

Responsibilities

* Read environment variables
* Validate required values
* Export typed configuration

---

# 14. Environment Generator

Generates

```text
.env.example
```

Only required variables are included.

Example

```text
BASE_URL=

API_KEY=
```

Unused variables are omitted.

---

# 15. Package Generator

Generates:

```text
package.json
```

Includes:

* project metadata
* scripts (`build`, `start`)
* runtime dependencies:
  * `@modelcontextprotocol/sdk` (required)
  * `axios`
* development dependencies

Dependency versions are centrally managed.

---

# 16. TypeScript Config Generator

Generates:

```text
tsconfig.json
```

Rendered from a **fixed static template**. No dynamic logic.

The Project Builder may copy a checked-in template file; the output must be identical on every run.

---

# 17. Docker Generator

Generates

```text
Dockerfile
```

Requirements

* Node LTS
* Install dependencies
* Build
* Start server

Dockerfile is rendered from a template.

---

# 18. README Generator

Generates

```text
README.md
```

Sections

1. Overview
2. Installation
3. Configuration
4. Environment Variables
5. Running the Server
6. Docker
7. Example Usage
8. Troubleshooting

---

# 19. Template Engine

Every generator uses the Template Engine.

Pipeline

```text
ViewModel

↓

Handlebars Template

↓

Generated File
```

Templates contain presentation only.

No business logic.

---

# 20. Formatting

Every generated source file is formatted using Prettier before being added to the GeneratedProject.

Formatting failures are fatal.

---

# 21. Validation

Before generation completes, the generator validates:

* Duplicate filenames
* Missing templates
* Missing required ViewModel fields
* Invalid output paths

Generation stops on validation failures.

---

# 22. Logging

Each generator logs:

* Start
* Finish
* Duration
* Generated file count
* Warnings

Example

```text
[Tool Generator] Generated 14 tool files

[README Generator] Completed

[Docker Generator] Completed
```

---

# 23. Statistics

Generation statistics include:

* Endpoint count
* Tool count
* File count
* Warning count
* Generation duration

Statistics are runtime metadata and are not written into generated source files.

---

# 24. Error Handling

Each module returns:

```ts
Result<T>
```

Generators never throw business exceptions.

Errors propagate to the Project Builder and then to the application entry point.

---

# 25. Determinism

For identical `ApiModel` input:

* Identical filenames
* Identical directory structure
* Identical file contents
* Identical generation order

Generators must never include:

* timestamps
* UUIDs
* machine-specific paths
* random ordering

---

# 26. Generator Dependency Rules

Allowed

```text
Generator

↓

ViewModel Builder

↓

Template Engine
```

Not allowed

* Generator → Parser
* Generator → Loader
* Generator → OpenAPI
* Template → ApiModel

All generators depend only on the IR and ViewModels.

---

# 27. Extension Strategy

Future generators must implement the common Generator interface.

Examples:

* Python Generator
* Test Generator
* GitHub Actions Generator
* Kubernetes Generator

No changes to the Parser or IR should be required.

---

# 28. Definition of Done

The Generator is complete when:

* A valid `ApiModel` produces a compilable TypeScript MCP server.
* Every Endpoint generates one tool file.
* All required project files are produced.
* Templates receive only ViewModels.
* Authentication is generated from the IR.
* Output is deterministic.
* The generated project builds without manual modification.
