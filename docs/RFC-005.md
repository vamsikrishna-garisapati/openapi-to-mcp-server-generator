# RFC-005: Parser Implementation Specification

**Project:** OpenAPI MCP Server Compiler

**Version:** 2.0 (Architecture Freeze)

**Status:** Approved

---

# 1. Purpose

This document specifies the **implementation details** of the Parser.

Behavioral rules are defined in **RFC-002**. The data contract is defined in **IR.md**.

---

# 2. Public Interface

The parser exposes one public method.

```ts
interface Parser {
    parse(document: RawDocument): Promise<Result<ApiModel>>;
}
```

No other public methods are exposed.

---

# 3. Internal Architecture

```text
Parser
│
├── JsonParser
├── Validator
├── RefResolver
├── MetadataExtractor
├── ServerExtractor
├── AuthExtractor
├── EndpointExtractor
├── SchemaExtractor
├── ResponseSelector
├── NamingEngine
└── IRBuilder
```

Every component has exactly one responsibility.

---

# 6. Validation Stage

Responsibilities:

* Validate OpenAPI version (3.0.x / 3.1.x)
* Validate required sections
* Validate operations and schemas
* **Reject duplicate `operationId` values (fatal E006)**

Fatal validation stops parsing. Warnings continue.

---

# 7. Reference Resolution

Responsibilities

* Resolve internal `$ref`
* Resolve nested references
* Detect circular references

Output contains no unresolved references.

---

# 8. Metadata Extraction

Extract

* title
* version
* description

Populate `ApiInfo`.

---

# 9. Server Extraction

Rules:

* Version 1 supports exactly one server
* Selection: `servers[0].url`
* If `servers` is missing or empty:
  * Set `ServerConfig.baseUrl = ""`
  * Emit warning **P004**
  * Generated project requires runtime `BASE_URL` (see IR.md §6)

---

# 10. Authentication Extraction

Supported:

* API Key
* HTTP Bearer

Extract into IR `Authentication`:

* `id`, `type`, `location`, `parameterName`, `envVariable`

Bearer normalization (always):

* `location = "header"`
* `parameterName = "Authorization"`
* `envVariable = "ACCESS_TOKEN"`

### Security assignment

For each endpoint, set `Endpoint.authentication`:

1. Apply global OpenAPI `security` by default
2. Operation-level `security` overrides global
3. `security: []` → `authentication: []`
4. No security defined → `authentication: []`

Unsupported authentication schemes produce warning **P003**.

---

# 11. Endpoint Extraction

Each operation becomes one Endpoint.

Extract

* method
* path
* summary
* description
* tags
* parameters
* request body
* responses

No naming occurs here.

---

# 12. Naming Engine

Input: extracted endpoints (no `id` or `name` yet)

Output:

* `Endpoint.id`
* `Endpoint.name` (same as `id` in Version 1)

Rules:

1. Use `operationId` if present
2. Otherwise derive from HTTP method + path
3. Convert to snake_case
4. Suffix derived-name collisions: `_2`, `_3`, …

Duplicate `operationId` is rejected in validation (E006) before this stage runs.

Naming occurs exactly once.

---

# 13. Response Selection

Each endpoint receives

```text
primaryResponse
```

Priority

1. 200
2. 201
3. default
4. first response

The Generator never repeats this logic.

---

# 14. Schema Extraction

Supported

* object
* array
* string
* integer
* number
* boolean
* enum
* nullable
* examples
* defaults

Unsupported constructs generate warning **P002** and are not represented in the IR.

---

# 15. Deprecated Endpoints

If `deprecated: true` on an operation:

* Include the endpoint in the IR
* Emit warning **P005**
* Generators append `(Deprecated)` to the tool description (RFC-001)

---

# 16. IR Builder

The final stage.

Responsibilities

* Build immutable ApiModel
* Validate internal consistency
* Return ParseResult

No OpenAPI objects are returned.

---

# 17. Warning Codes

Examples

```text
P001 Missing Description

P002 Unsupported Schema

P003 Unsupported Authentication

P004 Missing Server

P005 Deprecated Endpoint
```

Warnings never stop parsing.

---

# 18. Error Codes

Examples:

```text
E001 Invalid OpenAPI
E002 Missing Paths
E003 Invalid Schema
E004 Unresolved Reference
E005 Unsupported OpenAPI Version
E006 Duplicate operationId
```

Errors stop parsing immediately.

---

# 19. Performance Requirements

Small specification

< 2 seconds

Medium specification

< 5 seconds

Large specification

< 20 seconds

Memory usage should scale approximately linearly with document size.

---

# 20. Unit Testing

Every parser component must have dedicated unit tests.

Examples

* Validator tests
* Resolver tests
* Naming tests
* Schema extraction tests
* Authentication tests
* Response selection tests

---

# 21. Integration Testing

End-to-end parser tests should include:

* Petstore OpenAPI
* GitHub API
* Stripe API
* Small custom API
* Broken OpenAPI documents

Each test verifies the produced `ApiModel`.

---

End-to-end generation golden tests are specified in RFC-006.

---

# 22. Definition of Done

The Parser implementation is complete when:

* All parser stages are implemented.
* A valid OpenAPI document produces a valid `ApiModel`.
* No OpenAPI-specific objects leave the Parser.
* Warning and error reporting is standardized.
* Unit and integration tests pass.
* Performance targets are met.
