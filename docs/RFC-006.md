# RFC-006: Pipeline Orchestrator and Apify Actor

**Project:** MCP Studio

**Version:** 1.0 (Architecture Freeze)

**Status:** Approved

---

# 1. Purpose

This RFC defines:

* The **Pipeline Orchestrator** that wires public modules together
* The **Apify Actor** input/output contract for Version 1 deployment
* **End-to-end golden-file tests** required by the PRD Definition of Done

---

# 2. Pipeline Orchestrator

## Interface

```ts
interface PipelineOrchestrator {
    run(input: InputSource): Promise<Result<Archive>>;
}
```

Defined in RFC-004 §11.

## Responsibilities

1. Create a temporary workspace directory
2. Invoke modules in strict order
3. Aggregate warnings and statistics from each stage
4. Return the ZIP archive on success
5. Delete the workspace on completion (success or failure)
6. Never persist user specifications or generated projects after the run

## Execution Flow

```text
InputSource
      │
      ▼
Loader.load()
      │
      ▼
Parser.parse()
      │
      ▼
Generator.generate()      ← MCP Generator (RFC-003)
      │
      ▼
ProjectBuilder.build()
      │
      ▼
Packager.package()
      │
      ▼
Result<Archive>
      │
      ▼
Cleanup workspace
```

If any stage returns `success: false`, the orchestrator stops immediately and propagates errors upward.

Warnings from all stages are merged into the final result.

## Folder Location

```text
src/orchestrator/
    orchestrator.ts
    types.ts
```

## Logging

The orchestrator logs each stage start/finish and total duration:

```text
[Orchestrator] Loading specification...
[Orchestrator] Parsing complete (18 endpoints, 2 warnings)
[Orchestrator] Generating project...
[Orchestrator] Packaging ZIP...
[Orchestrator] Done (4.2s)
```

# 3. Apify Actor (Version 1 Deployment)

Version 1 runs MCP Studio as an **Apify Actor** — the generator itself is hosted on Apify.

> This is **not** the same as the PRD future feature "Apify Actor wrapper mode", which would generate MCP servers that expose existing Apify Actors as tools.

## Actor Input

```json
{
    "openApiSpec": "<string: JSON or YAML content>",
    "format": "json | yaml",
    "projectName": "<optional string, default from ApiInfo.title>"
}
```

| Field           | Required | Description                                      |
| --------------- | -------- | ------------------------------------------------ |
| `openApiSpec`   | Yes      | Full OpenAPI specification as a string           |
| `format`        | Yes      | `"json"` or `"yaml"`                             |
| `projectName`   | No       | Override generated project name (slugified)      |

The Actor passes input to the orchestrator as:

```ts
{ type: "string", content: input.openApiSpec }
```

with format detection from the `format` field.

## Actor Output

On success:

```json
{
    "success": true,
    "downloadUrl": "<URL to ZIP in Apify key-value store>",
    "statistics": {
        "endpointCount": 18,
        "toolCount": 18,
        "fileCount": 42,
        "warningCount": 2,
        "durationMs": 4200
    },
    "warnings": [
        { "code": "P004", "message": "No servers defined; BASE_URL required at runtime" }
    ]
}
```

On failure:

```json
{
    "success": false,
    "errors": [
        { "code": "E006", "message": "Duplicate operationId: getUser", "location": "paths./users.get" }
    ],
    "warnings": []
}
```

## ZIP Delivery

* The Packager produces a ZIP buffer
* The Actor stores it in Apify key-value store under key `mcp-server.zip`
* `downloadUrl` points to the stored artifact
* No persistent database; workspace is deleted after each run

## Security

* The Actor never stores API credentials from the uploaded spec
* Generated code reads secrets from environment variables only
* Uploaded specifications are not retained after the run completes

# 4. Local CLI (Optional)

The same orchestrator may be exposed as a local CLI for development:

```bash
mcp-studio generate --input spec.yaml --output ./out.zip
```

The CLI uses `{ type: "file", path: input }` and writes the ZIP to disk. Behavior is identical to the Actor pipeline.

# 5. Golden-File Tests

The PRD requires automated tests covering **parsing and generation** for representative OpenAPI specifications.

## Parser golden tests

Location: `tests/parser/`

* Input: OpenAPI fixture files
* Output: expected `ApiModel` JSON snapshots
* Verify IR invariants from IR.md

Fixtures:

* `petstore.yaml` (minimal valid spec)
* `auth-api-key.yaml` (header and query API keys)
* `auth-bearer.yaml`
* `no-servers.yaml` (empty baseUrl + P004)
* `deprecated-endpoint.yaml`

## Generation golden tests

Location: `tests/generation/`

* Input: pre-built `ApiModel` fixtures (or parse + generate end-to-end)
* Output: expected generated file tree snapshot
* Run `npm install && npm run build` in generated output as CI verification

Fixtures:

* Same OpenAPI inputs as parser tests, full pipeline to ZIP
* Compare file paths and contents against committed snapshots

## Snapshot rules

* Snapshots must be deterministic (no timestamps in generated source)
* Update snapshots only with intentional spec or generator changes
* CI fails on snapshot mismatch

## CI pipeline

```text
Unit tests (parser components)
      ↓
Parser integration tests
      ↓
Generation golden tests
      ↓
Build generated project (npm run build)
```

# 6. Error Handling

The orchestrator returns a single `Result<Archive>`:

* `success: true` — ZIP in `data`, warnings may be present
* `success: false` — `errors` populated, no ZIP

The Apify Actor maps this to the output schema in Section 3.

# 8. Definition of Done

RFC-006 is complete when:

* Orchestrator runs the full pipeline end-to-end
* Apify Actor accepts defined input and returns ZIP or structured errors
* Golden-file tests cover parser and generation for representative specs
* Generated projects build in CI without manual edits
* Workspace cleanup runs on every execution path
