# RFC-001: Generation Rules (Revised)

**Project:** OpenAPI MCP Server Compiler

**Version:** 2.0 (Architecture Freeze)

**Status:** Approved

---

# 1. Purpose

This RFC defines the deterministic transformation rules that convert an **ApiModel (IR)** into a complete MCP server project.

Generators **never** read OpenAPI documents.

All generation decisions are based solely on the Internal Representation (IR).

---

# 2. Responsibilities

The Generator is responsible for:

* Rendering templates
* Creating MCP tool files
* Creating project configuration
* Creating documentation
* Creating deployment files
* Creating environment templates

The Generator is **not** responsible for:

* Parsing OpenAPI
* Validation
* Endpoint naming
* Authentication normalization
* Primary response selection
* Schema normalization

Those responsibilities belong to the Parser.

---

# 3. Input

Input:

```text
ApiModel
```

Output:

```text
Generated Project
```

---

# 4. Pipeline

```text
ApiModel
      │
      ▼
ViewModel Builder
      │
      ▼
Template Renderer
      │
      ▼
Generated Files
```

Every generator follows this pipeline.

---

# 5. Endpoint Generation

Every `Endpoint` becomes exactly one MCP Tool.

Example

```text
Endpoint

↓

Tool
```

Tool name:

```text
Endpoint.id
```

Tool description priority:

1. Endpoint.description
2. Endpoint.summary
3. Generated fallback

The generator never derives names from HTTP methods or paths.

### Deprecated endpoints

If `Endpoint.deprecated` is `true`, append `(Deprecated)` to the tool description. The tool file is still generated.

---

# 6. Tool Files

Version 1 generates one file per endpoint.

Example:

```text
src/tools/

create_user.ts

update_user.ts

delete_user.ts
```

Grouping by tags or resources is out of scope for Version 1.

---

# 7. MCP Tool Definition

Each generated tool contains:

* Tool name
* Tool description
* Input schema
* Handler
* Error handling

The tool definition is built entirely from the Endpoint object.

---

# 8. Input Schema Generation

The generator converts:

```text
Endpoint.parameters

+

Endpoint.requestBody
```

into one MCP Input Schema.

Mapping rules:

* Path parameters → Required inputs
* Query parameters → Optional unless marked required
* Header parameters → Optional inputs (except authentication headers)
* Cookie parameters → Ignored in Version 1

Authentication headers are never exposed as tool inputs.

---

# 9. Authentication

The generator uses:

```text
Authentication
```

from the IR.

Behavior:

### API Key

Insert credential according to:

* location
* parameterName

Example:

Header

```text
X-API-Key
```

↓

```text
headers["X-API-Key"]
```

Query

↓

Append query parameter.

Cookie

↓

Insert cookie.

---

### Bearer

Always generate:

```text
Authorization: Bearer TOKEN
```

using the configured environment variable.

The generator never infers authentication.

---

# 10. Response Handling

The generator always uses:

```text
Endpoint.primaryResponse
```

It never chooses between:

* 200
* 201
* default

Those decisions were made by the Parser.

---

# 11. Schema Mapping

Input:

```text
Schema
```

↓

Output:

```text
JSON Schema
```

Supported:

* object
* array
* string
* integer
* number
* boolean
* enum
* default
* nullable
* examples

Unsupported schema features are ignored because they never appear in the IR.

---

# 12. HTTP Client

Generate one shared HTTP client.

Responsibilities:

* Base URL
* Authentication
* JSON serialization
* Timeout
* Error conversion

Retries are not included in Version 1.

---

# 13. Error Handling

Every generated tool follows the same pattern:

```text
Validate Input

↓

Execute Request

↓

Return Result

↓

Catch Error

↓

Return Friendly Error
```

Generated code must not expose stack traces to MCP clients.

---

# 14. Environment Variables

Generate `.env.example`.

Include only variables required by the Authentication objects.

Examples:

```text
BASE_URL=

API_KEY=

ACCESS_TOKEN=
```

Unused variables must not be generated.

---

# 15. README Generation

README always contains:

1. Project Overview
2. Installation
3. Environment Variables
4. Running the Server
5. Example Usage
6. Docker
7. Troubleshooting

This structure is fixed.

---

# 16. Docker Generation

Generate one Dockerfile.

Requirements:

* Node LTS
* Install dependencies
* Build
* Start server

The Dockerfile is rendered from a template.

---

# 17. package.json Generation

Generate automatically.

Include:

* Project metadata
* Scripts (`build`, `start`)
* Runtime dependencies:
  * `@modelcontextprotocol/sdk` (official MCP SDK — required)
  * `axios`
* Development dependencies (`typescript`, `@types/node`, `prettier`, etc.)

Dependency versions come from centralized configuration.

---

# 18. Formatting

Every generated source file is formatted with Prettier before writing.

Formatting errors are fatal.

---

# 19. View Models

Templates never receive `ApiModel`.

Generators first build ViewModels.

Example:

```text
Endpoint

↓

ToolViewModel

↓

tool.hbs
```

This keeps templates simple and free of business logic.

---

# 20. Determinism

For identical IR input:

* File names must be identical
* File contents must be identical
* Generation order must be identical

Generators must not introduce:

* Random values
* UUIDs
* Current timestamps
* Machine-specific paths

---

# 21. Warnings

Generators may emit warnings for:

* Missing descriptions
* Unsupported optional metadata
* Empty examples

Warnings never modify generation behavior.

---

# 22. Fatal Errors

Generation stops if:

* Required templates are missing
* Duplicate file names are produced
* Invalid ViewModels are created
* Required Authentication information is absent

---

# 23. Generator Responsibilities Matrix

| Responsibility           | Parser | Generator |
| ------------------------ | :----: | :-------: |
| Validate OpenAPI         |    ✅   |     ❌     |

| Choose Endpoint Names    |    ✅   |     ❌     |
| Select Primary Response  |    ✅   |     ❌     |
| Normalize Authentication |    ✅   |     ❌     |
| Build ViewModels         |    ❌   |     ✅     |
| Render Templates         |    ❌   |     ✅     |
| Write Files              |    ❌   |     ✅     |

---

# 24. Version 1 Scope

Version 1 supports:

* REST APIs
* OpenAPI 3.x
* JSON request bodies
* API Key authentication
* Bearer authentication
* TypeScript MCP servers

Future RFCs will define:

* OAuth
* Multipart requests
* Streaming APIs
* Python generation
* AI-assisted enhancements

---

# 25. Definition of Done

RFC-001 is complete when:

* Generators depend only on `ApiModel`.
* No generation logic references OpenAPI.
* Authentication is driven entirely by the IR.
* Every Endpoint generates one MCP tool.
* Templates contain presentation logic only.
* Generated output is deterministic and reproducible.
